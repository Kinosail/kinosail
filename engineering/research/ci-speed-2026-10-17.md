# CI speed reset — 2026-10-17

## Measured problem

Five complete `ci.yml` runs from 2026-10-17 were read job by job (created, started, and completed times from the Actions API). Only green runs were included.

| Run | Event | Wall clock | Jobs that ran | Runner minutes | Queue minutes |
| --- | --- | --- | --- | --- | --- |
| 38998504705 | push to main | 89 min | 46 | 90 | 382 |
| 39001445665 | pull request #677 | 42 min | 44 | 101 | 287 |
| 38995229260 | pull request #676 | 56 min | 33 | 72 | 441 |
| 39002660559 | merge group #674 | 34 min | 37 | 81 | 256 |
| 38999839728 | merge group #676 | 35 min | 33 | 72 | 211 |

The runners did 70 to 100 minutes of work per run. The jobs waited 200 to 440 minutes in queue. The organization is on the GitHub Free plan for a public repository, which allows 20 concurrent jobs for the whole organization. Each run created 33 to 60 jobs, and a pull request push, its merge group run, and the main push each ran the full suite. Three or four runs in flight exhausted the 20 slots, so every job waited.

The critical path made this worse. Each pull request went plan → image → browser → suite complete → Player checks, and each arrow was a new runner allocation that waited in the same queue. On the 89 minute main push, the two aggregator hops alone waited 39 minutes, and publication then rebuilt and re-verified everything after a further 15 minutes of hops.

The longest single jobs were the Player populated Chromium smoke (10.5 min, of which the single-worker populated settings suite was 3 min), the Player quick Go tests (6.7 min, 5.8 min of it `internal/server`), the installer and local pipeline (6 min), and the media proof shards (3 to 10 min).

The `layout-stability.yml` workflow also started three 20 minute jobs on every pull request that touched the servers or shared web packages. It is not a required check.

## Decisions

1. One fast workflow (`ci.yml`) for pull requests, the merge queue, and main. It creates about 11 jobs for a Player change instead of about 40: plan, repository policy, Go per module, E2E per app and phase, four media proof shards, and the four required aggregators. The arm64 container, installer, Swift, Android, and docs jobs run only when their inputs change.
2. The merge queue is the test of record. GitHub's merge queue fast-forwards `main` to the exact commit it tested, so a push to `main` has a successful `merge_group` run for the same SHA. The plan job looks that run up. When it exists, the push run skips every test job and only runs the Security scans (so CodeQL keeps analyzing `main`), the docs build, and publication. `delivery.py` repeats the lookup before any image is pushed. A direct push without a queue run still gets the complete suite.
3. Native parallel steps replace small jobs. Lint, tidy, vulnerability, and tests for one Go module share one runner. Policy checks, tooling tests, and script lint share one runner. Each E2E job builds its own cached amd64 image in parallel with Playwright installation instead of a separate image job plus an artifact round trip.
4. The Player browser smoke is split into two phases on two runners: `journeys` (Go-driven journeys, the `@smoke` suite, native intent) and `populated` (the single-worker populated settings suite). `KINOSAIL_BROWSER_PHASE` selects the phase; the default `all` keeps local behavior.
5. Publication merges manifest signing and production promotion into one serialized job that keeps the `Advance <app> production tags` name the Nox deployment watchers read.
6. Everything weekly moved to `deep.yml`: race and coverage, the complete Chromium, Firefox, and WebKit suites, the iOS and tvOS native contracts, the Android emulator and Wear journeys, full-history secret scanning, Swift CodeQL, and the deep quality metrics. `ci.yml` has no `deep` conditionals.
7. `layout-stability.yml` runs weekly, on dispatch, and on pull requests labeled `layout-evidence`.

## Expected effect

With no queue wait, a Player pull request's critical path is plan → E2E journeys → Player checks, about 10 to 13 minutes. With about 11 jobs per run, two runs fit inside the 20 slot limit without waiting, and the main push frees its slots within a few minutes. These are projections from the measured job durations; measure at least 20 green runs per event before claiming a number.

## First hosted run

Pull request #686 changed every workflow file, so its run selected everything (run 39007700217, commit fdeceb01):

| Measure | Old full PR runs | New pipeline |
| --- | --- | --- |
| Wall clock | 42 to 56 min | 17 min (14 min from the first job's creation) |
| Jobs that ran | 33 to 44 | 29, four of them aggregators |
| Runner minutes | 72 to 101 | 91 |
| Queue minutes | 287 to 441 | 56 |

Longest jobs: Go (player) 8.0 min, Media proof (audio-splice) 8.5 min, CodeQL compiled languages 8.2 min, E2E (player journeys) 6.9 min, E2E (player populated) 6.2 min. The Go (player) job is now the critical path: lint, govulncheck, and the quick tests share four cores, so the tests took 8.0 min instead of 6.7. A Player change that does not touch workflows skips the Android, Swift, arm64, and installer jobs and the CodeQL compiled job runs only for Go. The remaining queue minutes came from the cancelled first attempt still occupying slots when this run started.

The first attempt failed in one job: CodeQL refuses one `init` with mixed build modes. Interpreted languages now run with `build-mode: none` in the Security scans job, and Go plus Java/Kotlin run with `build-mode: manual` in a separate CodeQL compiled languages job.

## Follow-ups that need an administrator

- Switch the required status checks from the four aggregator names to the real job names (`Select affected components`, `Repository policy and tooling`, `Go (player)`, `E2E (player journeys)`, and so on) and then delete the aggregator jobs. GitHub treats a job skipped by its `if` as a passing required check, and the plan job being required keeps a broken selection from passing silently. This removes one more queue hop per run.
- Consider a GitHub Team plan (60 concurrent jobs) or a support request for a higher concurrency limit if more than two pull requests are usually in flight.
- "Require branches to be up to date before merging" is still on. The merge queue already tests every entry against current `main`, so this setting only forces extra pull request runs.

## Not verified here

Hosted timings of the new jobs, the `parallel:` composite-action combination inside the E2E jobs, and `deep.yml` on its first scheduled run need run evidence. The weekly workflow could not be dispatched from a branch before merge.
