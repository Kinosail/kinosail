# Web player performance audit — 2026-10-16

Scope: the Player web app's core playback path (page load, browser runtime, direct play, HLS transcode pipeline, image delivery, browse rendering, and host runtime). Five read-only code reviews covered one subsystem each; every finding below was then confirmed against the source or measured against a local populated instance built from `ce2f814` with the generated test media. Line numbers refer to that revision.

## Changes made in this task

1. **`hls.min.js` is served under a content hash.** The vendored file is hls.js 1.7.3 (`THIRD_PARTY_NOTICES.md`, dependency integrity pin) but every reference said `?v=1.7.1` with `public, max-age=31536000, immutable`. Browsers that cached the earlier build at that URL kept running it for a year after the upgrade, and the next upgrade would repeat the problem. The template head tag, the lazy loader in `player.js`, and the browse-page prefetch in `startup-preparation.js` now carry `sha256(hls.min.js)`, through the same `assetVersions` seam that already hashes `app.css`, `theme.js`, and the main bundle.
2. **Static assets send `ETag` and answer `If-None-Match` with 304.** `compressedAsset` had no validator, so every unversioned asset (`cinema-backdrop.jpg`, manifest, icons) and every service-worker `cache: "reload"` shell fetch re-sent the full body after `max-age` expired. Identity and gzip representations carry distinct tags.
3. **The service worker revalidates private images instead of re-downloading them.** `/art`, `/backdrop`, and `/person` are served `no-store` by design and cached per Viewer Profile inside the service worker. The background refresh fetched each hit again in full; it now sends `If-Modified-Since` from the cached `Last-Modified`, and the server's `http.ServeFile` answers 304 with no body. On a 100-card browse page this removes the full poster payload on every repeat view.
4. **HLS transcode filters are no longer pinned to one thread.** `hls_presentation.go` passed `-filter_threads 1 -filter_complex_threads 1` for every video transcode, so CPU scaling, deinterlacing, and the float HDR-to-SDR tone-map chain ran single-threaded at source resolution before the per-rung downscale. Both flags now follow the same per-rung thread budget as the encoder (`GOMAXPROCS / rungs`, capped at 2 during prewarm), so a transcode never uses more cores than the admission governor planned for it.
5. **hls.js keeps a bounded back buffer and skips low-latency setup.** The 1.7 defaults inherited by the player were `backBufferLength: Infinity` and `lowLatencyMode: true`. Infinite back buffer pushes TV and phone browsers into `QuotaExceededError` eviction cycles on long films; low-latency mode installs part loaders that VOD playlists never use. The player now sets `backBufferLength: 90` and `lowLatencyMode: false`.
6. **The stall watchdog no longer discards a stream that is still receiving data.** After 12 seconds of `waiting` the recovery code reloaded the source or restarted the hls.js session even when `progress` events were arriving and `buffered` was growing. That threw away buffered bytes and, for compatible playback, started a new transcode session at a new origin. The watchdog now defers once per 12 seconds while data is arriving, for at most 60 seconds, and then falls back to the existing retry and failure path. The existing fixture tests that simulate a dead stream still see the retry after 12 seconds.
7. **The `/watch` handler skips library-wide work that cannot apply.** Every player page copied the visible library three times. The audio queue is now computed only for `audio` items and the next-Episode lookup only for Episodes, which removes two full-library snapshots and one `Organize` pass from every movie page.

## Findings left for follow-up, ranked by expected hardware gain

Update after reconciling with `origin/main` at `440268f`: main landed parallel work that covers several items below. Pull request #641 verifies hardware decode per codec and keeps 10-bit HEVC HDR on the device (item 1), fixes the VideoToolbox quality scale and adds NVENC and QSV presets (item 4); `presentationFilterGraph` in `hls_presentation.go` shares one filter chain across rungs (item 2); #652 charges ladder cost through `workload.LadderCost` (item 3); #645 makes localized templates lazy (item 7); #646 and #648 replace per-request library copies with `visibleView` and store Player metadata per record (items 8 and 13 in part). The list is kept as the audit found it; treat those items as landed or in progress rather than open.


1. **Hardware decode is only used for 8-bit SDR H.264.** `packages/playback/hls_source.go:181` (`testedDecodeInput`) and `transcodehardware/verification.go:154-168` verify and enable hardware decode for H.264 alone, and `HardwareDecode` is cleared whenever a tone map, deinterlace, or software filter is present. Every HDR recipe starts with `format=p010le,hwupload`, so 4K HEVC 10-bit sources decode on the CPU on QSV, NVENC, VA-API, RKMPP, and VideoToolbox hosts. This is the largest unrealized gain on N100, RK3588, Jetson, and discrete-GPU hosts. Fix: verify decode per codec (`h264`, `hevc`, `hevc10`, `av1`) with synthetic clips at startup, store a per-codec decode map, and feed hardware frames directly into `vpp_qsv`, `tonemap_cuda`, and `tonemap_vaapi`. Keep Dolby Vision profile 5 and software-filter recipes on the CPU and rely on the existing software fallback in `hls_recovery.go`. This needs device evidence and was not attempted here.
2. **Per-rung filter duplication.** Each ladder rung repeats the full `-vf` chain (`hls_presentation.go:56-60`), so a three-rung CPU HDR or burned-subtitle transcode tone maps or renders subtitles three times. One `-filter_complex` with a shared prefix and `split` would decode and filter once.
3. **Playback admission can wait behind background work.** `workload.HeavyCapacity()` is `min(3, GOMAXPROCS-1)`; the CPU ladder is trimmed to that capacity (`hls.go:253-262`) and charged one unit per rung, so a full ladder needs every slot while a scan or probe holds a background slot. On one- and two-core hosts the single slot can be held by a scan for its whole duration. Options: size the playback ladder to `capacity - background` so one playback transcode is always admissible, or make the scan release its slot between batches when `WaitingPlayback > 0`.
4. **Encoder tuning per backend.** VideoToolbox receives `-q:v 22` on its 1–100 scale, which is a low-quality setting; QSV has no `-low_power 1` on Gen11+ and no preset; NVENC uses a fixed `-preset p4` without `-rc vbr -cq -b:v 0 -spatial-aq 1`; VA-API uses CQP so `-maxrate` is ignored. Each is a few arguments in `transcodepolicy/arguments.go` but needs device verification.
5. **Startup latency.** The first segment is 2 seconds with a 2-second keyframe grid and no `-hls_init_time`; a 1-second first segment would cut cold start by about a second at a small bitrate cost. `hlsmanifest.CompleteVOD` assumes 2-second segments, so the projection must change with it.
6. **Copied-video startup reads the whole file.** The H.264 keyframe index runs `ffprobe -show_packets` plus two framehash passes over the entire file per recipe key (`mediaprobe/h264_packets.go`, `h264_certification.go`); a 40 GB remux on a NAS costs minutes of sequential I/O, and a cold resume waits up to 8 seconds before failing with `errCopiedHLSIndex`. Cache the index per source version and merge the certification passes.
7. **Every HTML render clones and re-escapes the template set** (`packages/localization/template.go:51-66`) to inject per-request funcs. Passing the CSRF token and picker through the data would remove 1–3 ms and tens of thousands of allocations per page on desktop, several times that on a Raspberry Pi.
8. **Landing page passes.** `/` copies the whole visible library at least twice, sorts the whole library for history with string concatenation in the comparator, and runs seven shelf passes plus three `Organize` calls. A single decorated pass and a shared `Organize` result would hold landing cost flat for 10k-item libraries.
9. **Render-blocking `theme.js` carries about 30 KB that gates on `DOMContentLoaded`.** Splitting it is blocked by 27 pages that load `theme.js` without the main bundle; moving those pages onto the bundle first would let the sync script shrink to the theme and layout-initial scripts.
10. **hls.js light build.** The player uses no alternate-audio groups, EME, or CMCD, so `hls.light.min.js` (roughly 60% of the size) is viable. It changes a reviewed third-party artifact hash and should land as its own reviewed dependency update.
11. **Brotli for precompressed assets.** Gzip is precompressed at startup; a pure-Go brotli encoder at startup would save about 15–20% more on the 360 KB gzip cold load. It adds a Go dependency and startup CPU.
12. **Trickplay sprite sheets.** Scrubbing requests one JPEG per 10-second bucket, each a separate `ffmpeg -ss` launch through one background slot. One tiled pass per item after scan plus a WebVTT thumbnail track would make first scrub instant.
13. **`index.Safe` resolves symlinks on every file request** (`packages/library/access.go:41-44`, `catalog/scan.go:14-27`), twice per image. Caching the root resolution and the per-item verdict keyed by size and mtime would remove tens of `lstat` calls per poster on NAS mounts while keeping the symlink guard.
14. **Embedded subtitle extraction** demuxes the whole file through ffmpeg without a governor slot (`mediaprobe/embedded.go:161`).
15. **Library poller** stats every file every 30 seconds even while fsnotify is healthy (`catalog/watch.go:19-27`).
16. **Client negotiation** sends only `videoCodecs`; the API already accepts audio codecs, HDR formats, and channel counts (`api_product.go:271-296`), so audio and HDR direct-play decisions fall back to user-agent sniffing. The negotiation budget is 1.5 seconds including the server round trip (`player.js:88-95`).
17. **Playback trace flush** sends one POST per queued event (`player-core.js:38-50`); a batched body would cut request count during buffering.
18. **Audio queue warm-up** creates a second `Audio` element per track and never releases the previous one (`player-audio-queue.js:107-110`).

Two items were reviewed and deliberately left unchanged: HTML gzip (pages carry CSRF tokens, so compressing them reopens BREACH-class attacks) and `synchronous=FULL` for SQLite (a durability choice that belongs to the Owner, not to a performance patch). The `no-store` policy on artwork is a privacy decision; the service worker's per-profile cache already gives repeat views cache-first posters, and change 3 removes the remaining background re-download.
